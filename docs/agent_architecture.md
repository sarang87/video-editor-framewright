# Agent Architecture: Stateful Narrative Brainstorming

The **Stateful Narrative Brainstorming** feature introduces an "Intelligence Layer" to FrameWright, enabling users to collaboratively build video edits using natural language. This system is architected to be:

1.  **Stateful**: Remembers conversation context and the evolving edit plan.
2.  **Reasoning-First**: Uses "Chain of Thought" to make creative decisions, not just keyword matching.
3.  **Tool-Augmented**: Directly queries the clip database and verifies asset availability.

## Core Components

The agent implementation resides in `app/agent/` and consists of four main layers:

### 1. State Management (`state.py`)
We use **LangGraph** to manage the state of the session. The state is defined as a TypedDict `FilmState`:

```python
class FilmState(TypedDict):
    messages: List[BaseMessage]  # Chat history
    user_intent: str             # Current narrative goal (e.g., "Create a happy intro")
    bin: List[dict]              # Candidate clips found via search
    timeline: List[dict]         # The Edit Plan (ordered list of selected clips)
```

**Checkpointing**: A `MemorySaver` persists this state between interactions, allowing the user to close the browser and resume later.

### 2. Narrative Planner (`planner.py`)
This is the "Brain" of the operation, powered by **DSPy**. 

- **Module**: `NarrativePlanner`
- **Logic**: It uses a `dspy.ChainOfThought` signature to transform `(user_intent, search_results)` into a structured `Edit Plan`.
- **Advantage**: Unlike standard prompt engineering, DSPy allows us to optimize the "prompt" (signature) programmatically and enforces structured reasoning.

### 3. Tooling (`tools.py`)
The agent interacts with the `DuckDB` metadata store through a set of tools:

- **`sql_search`**: Executes SQL queries generated by the agent to find clips based on visual descriptions, categories, or tags.
- **`validate_clips`**: (Planned) Verifies that the physical video files exist on disk before adding them to the timeline.

### 4. Orchestration (`graph.py`)
The control flow is defined as a dedicated graph:

1.  **Agent Node**: Acts as the router. It examines the current state and decides the next step:
    - If `bin` is empty -> **Search**.
    - If `bin` has clips but `timeline` is empty -> **Plan**.
    - If `timeline` exists -> **End** (or Validate).
2.  **Search Node**: Executes the `sql_search` tool.
3.  **Planner Node**: Invokes the DSPy `NarrativePlanner`.

## Data Flow

1.  **User Input**: "I want a high-energy intro with cars."
2.  **Streamlit UI**: Sends input to `AgentService`.
3.  **Agent Node**: Detects new intent, routes to **Search**.
4.  **Search Node**: Queries DuckDB for "cars", "high energy". Updates `state["bin"]`.
5.  **Agent Node**: Sees `bin` is populated, routes to **Planner**.
6.  **Planner Node**: Selects best clips from `bin`, orders them, assigns reasoning. Updates `state["timeline"]`.
7.  **UI**: Renders the new Timeline.

## Key Technologies
- **LangGraph**: Workflow orchestration and state persistence.
- **DSPy**: Declarative Language Model programming for robust reasoning.
- **DuckDB**: Fast, local SQL analytics for clip metadata.
- **vLLM / OpenAI**: The underlying LLM inference engine.
